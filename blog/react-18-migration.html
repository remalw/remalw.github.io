How we migrated to React 18 in production: lessons from a 6-month rollout

A frontend tech lead's notes on shipping React 18 across a 200k-line codebase without taking the site down.

We started the React 18 migration on a Tuesday in October. We finished — really finished, every team off the legacy pattern — six months later, the week before Easter.

This is the post-mortem I wish I'd had when we started. Not a tutorial. More like a field journal: what we expected to be hard, what was actually hard, and what surprised us.

Context

The codebase: ~200k lines of TypeScript across about 14 product surfaces, all hanging off a single host shell. Roughly 30 engineers contributing day to day. We were on React 17.0.2, with a well-loved pile of class components, custom HOCs, and a state management story that was 80% Redux Toolkit and 20% "we'll fix it later".

Goals for the migration:

  1. Get to React 18.2 across the board.
  2. Adopt automatic batching and useTransition where it actually helped.
  3. Don't break anything in production.

That's it. We deliberately didn't try to also adopt server components, Suspense for data fetching, or any of the new SSR streaming features. Scope discipline matters. You can do those later.

Phase 1: the easy part (weeks 1-3)

Bumping the dependency was painless. react@18.2.0, react-dom@18.2.0, types, done. Build passed. Tests passed.

Then we ran the app, and roughly 40% of our test suite turned red.

The reasons, in descending order of frequency:

  • act() warnings on async tests. React 18's stricter act() assertions caught a bunch of places where we had await Promise.resolve() instead of properly waiting on rendered effects. Mostly mechanical to fix.
  • ReactDOM.render deprecation. We had two test utilities still using the old API. Replaced with createRoot, moved on.
  • StrictMode double-invocation. This was the real one. We'd been running with for years but development mode in React 18 calls effects twice, and we had effects with non-idempotent side effects. About 20 components needed cleanup.

Two weeks in, all tests green, internal staging running. Felt good. Premature.

Phase 2: production rollout (weeks 4-10)

We didn't ship to 100% of users on day one. We shipped to 1%, behind a feature flag.

This is the part most migration guides skip. Your unit tests can be perfect and you can still find weird stuff in production. Examples we hit:

  • A third-party analytics library that monkey-patched Array.prototype and broke under automatic batching. Not React's fault, but it surfaced because of React 18.
  • A WYSIWYG editor that depended on synchronous DOM updates. With automatic batching, two state updates in the same event handler now produced one render instead of two, and the editor's internal selection logic relied on the intermediate state. Three days of debugging to find this.
  • A weird race in our analytics code where two useEffect calls fired in a different order under React 18's stricter scheduling. We had been relying on undocumented ordering.

The lesson: the dangerous part of a major React migration isn't the things React tells you have changed. It's the undocumented contracts your code was secretly depending on.

We rolled out 1% → 5% → 25% → 50% → 100% over six weeks, with a kill switch that could revert any user back to React 17 within 30 seconds. We used the kill switch twice. Both times the bug was ours, not React's.

Phase 3: the long tail (weeks 11-26)

By week 11, all users were on React 18. We could have called it done. Instead we entered the long tail: actually using the new features.

This is where most of the good came from.

Automatic batching

Mostly free. We had a few places where we'd manually wrapped multiple setState calls in unstable_batchedUpdates — those got cleaned up. We got a measurable reduction in re-renders across the app: roughly 30% fewer commits in our flame graphs on the dashboards.

useTransition

This was the killer feature. We had several search/filter UIs where typing in a textbox blocked the UI because filtering 10k items synchronously is slow. Wrapping the filter update in startTransition made these UIs feel instant — the textbox stays responsive, the list catches up when it can.

Hard-won lesson: don't put everything in a transition. Transitions are interruptible, which means your UI will look "jittery" if you wrap state that needs to be visible immediately. A good rule: keep input state out of transitions, put list/computed-derived state in.

Suspense for code splitting

We already used React.lazy. React 18's Suspense improvements meant we could render placeholder UIs without the cascade-of-spinners problem. Modest win, but a real one.

What I'd do differently

Start with the test suite, not the codebase. I'd spend the first week doing nothing but fixing act() warnings and StrictMode double-invocation issues, with the dependency not yet bumped. We did this in parallel and it created confusing noise.

Build the kill switch first, before any user sees React 18. We did this, but barely. If we hadn't, the WYSIWYG bug would have been much more painful.

Don't try to also "modernize" while you migrate. We had two engineers who, while migrating their team's components, also rewrote them in functional style. This was net-bad. The migration PRs should have been minimal — convert what's needed, don't refactor. Refactor later.

Budget for two months of "long tail" after the cutover. The actual migration takes one third of the calendar time. The other two thirds are adoption, fixing things you didn't know were broken, and capturing the wins.

Was it worth it?

Yes, but quieter than the marketing made it sound. Automatic batching gave us ~30% fewer renders, which translates to maybe a 5-10% improvement in mean frame time. useTransition made specific UIs feel dramatically better. Suspense was nice. Concurrent rendering didn't change much for us.

Bigger picture: we were on the supported version of React. We could pick up future features without first paying back tech debt. That alone justifies the work.
