Why TypeScript strict mode should be your default (and how to migrate without tears)

An opinionated case for strict mode, plus a migration playbook that won't blow up your sprint.

I have one strong opinion on TypeScript: "strict": true should be on from day one of any new project. If you inherit a codebase without it, migrating is one of the highest-ROI things you can do.

This isn't a controversial take in 2026. But every six months I still see a "we don't need strict mode, we're disciplined" post on Hacker News, and every six months it's wrong. Let me say why, then talk about migration.

The argument for strict mode

Strict mode is a bundle of seven flags. The two that matter most:

  • strictNullChecks — T no longer includes null and undefined. You have to handle those cases explicitly.
  • noImplicitAny — variables you don't annotate aren't silently typed any.

Together, they catch the two biggest classes of bugs that TypeScript-without-strict misses:

  1. Accidental undefined access. The "Cannot read property X of undefined" that 60% of your runtime errors are made of.
  2. Functions that look typed but aren't. You have a function with a parameter user that's implicitly any. You think you're refactoring safely. You're not.

People who say "I don't need strict mode" are usually saying "I am personally good enough to avoid these mistakes." Maybe you are. Your teammates, future-you, and the contractor who joins next month are not.

I'll go further: I've worked on three large codebases that turned strict mode on after-the-fact. In every case, the migration uncovered real bugs that had been in production for months — not theoretical issues, actual user-affecting bugs. Including, in one case, a billing bug.

What about other flags?

The remaining strict flags are easier:

  • strictFunctionTypes, strictBindCallApply — turn these on. They catch real bugs and rarely produce false-positive friction.
  • strictPropertyInitialization — class fields must be initialized. Annoying for the first day, fine after.
  • alwaysStrict — emits "use strict" in JS output. Free.
  • noImplicitThis — this must be typed. Almost never produces issues in modern code.

There are two non-strict flags you should also turn on after strict: true:

  • noUncheckedIndexedAccess — array and dictionary access returns T | undefined. This is spicy — it forces you to check every arr[i] access. But it eliminates an entire category of bugs.
  • exactOptionalPropertyTypes — distinguishes "missing key" from "key with undefined value". Niche, but useful for API contracts.

OK, you're sold. How do you migrate without ruining a sprint?

Here is the playbook I've used twice.

Don't try to flip all the flags at once

If your codebase has 1000+ TypeScript errors after enabling strict: true, you can't realistically fix them in one PR. You have two options:

  1. Big-bang migration. Lock the codebase, fix everything, ship. This is feasible only on small teams with small codebases. I've never seen it work on anything over 50k lines.
  2. Incremental migration. Enable one flag at a time, and within each flag, fix files in batches. This is what works.

The incremental approach uses one trick: turn the flag on, mark every existing error as @ts-expect-error, then fix the markers over time. This way:

  • The build passes.
  • No new code can introduce the same kind of error (it would be a real type error).
  • You can fix old code at your own pace.

The codemod helper

I wrote a small codemod for this — ts-strict-codemod. It does the marking automatically. But you can also do it by hand:

bash

# 1. Add the flag to tsconfig
# 2. Run tsc to get the errors
pnpm tsc --noEmit > errors.txt

# 3. For each error, add @ts-expect-error above the offending line
# (the codemod automates this)

# 4. Build passes again. Now fix on a schedule.

Migration order

Some flags produce more errors than others. Do them in this order:

  1. noImplicitAny — the cheapest. You add type annotations.
  2. strictNullChecks — the most important. Where most of your bugs are hiding.
  3. strictFunctionTypes, strictBindCallApply, alwaysStrict — usually clean.
  4. strictPropertyInitialization — class-heavy codebases will have noise here.
  5. noUncheckedIndexedAccess — last. This one is spicy.

For the 200k-line migration I led, this took six months of background work, alongside feature delivery. A small fraction of someone's time per week. Not blocking, not crash-priority. Just steady.

Wait — what about the codebase that's already strict-on but only 60% covered?

Some teams turn on strict: true but then sprinkle as any and // @ts-ignore everywhere. Those teams aren't really running strict mode. They're running a strict mode-shaped lie.

If that's you: you don't have a strict mode problem, you have a code review problem. Add a lint rule (@typescript-eslint/no-explicit-any, eslint-comments/no-use) that warns on any and @ts-ignore. Treat them as code smells. Require justification in the PR description for every one.

Common objections

"It slows us down." It speeds you up, after the first month. Bug-fix time is 30-50% lower in well-typed code in my experience. Initial annotation cost is real but small.

"Our types are too dynamic." Then your runtime is also too dynamic, and you should fix that first. TypeScript reflects what your code actually does. If strict makes that hard to type, your code is hard to reason about.

"any is fine sometimes." Yes. unknown is better.

What I actually do on a new project

jsonc

{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noFallthroughCasesInSwitch": true,
    "noImplicitOverride": true
  }
}

This is the config I copy-paste into every new project. It catches more bugs than the default. It costs me roughly five extra minutes per day of explicit null checks. The trade is wildly in my favor.

If you're considering migrating an existing codebase, do it. Start small, schedule it as ongoing work, and don't try to be a hero. Six months from now you'll have one fewer category of bug to chase down.
