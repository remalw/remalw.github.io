Three.js performance: how I cut WebGL frame time by 40%

Real techniques that moved real numbers on a real production scene. Not 'put everything in InstancedMesh'.

Most "Three.js performance" posts you find online are about toy scenes. The advice is the same in every one: use InstancedMesh, don't rebuild geometries every frame, merge static meshes. Good advice. Stops working when your scene has 200 unique meshes, dynamic lighting, and animated cameras.

This is what actually moved the needle for me on a production scene that was running at ~24 fps on the M1 baseline. I got it to ~40 fps. Not magic, just careful work.

The scene

For context: an interactive product gallery with around 80 model instances visible at any time, soft shadows, post-processing (bloom + SMAA), and a custom pointer-tracking interaction layer. Target was 60 fps on M1; we were sitting at 24 fps.

I'm not going to walk through every optimization. I'll talk about the four that gave the most return.

1. Stop computing matrices you're not using

If you have static meshes, set mesh.matrixAutoUpdate = false and call mesh.updateMatrix() once when you place them. By default, Three.js recomputes the matrix every frame for every object, even if nothing has moved.

In our scene we had 60 of those 80 meshes static. Disabling auto-update on those 60 dropped per-frame matrix computation cost by about 1.2ms on average — which on a 16.6ms budget is 7% of your frame time, recovered for free.

ts

scene.traverse((obj) => {
  if (obj.isMesh && !obj.userData.isAnimated) {
    obj.matrixAutoUpdate = false;
    obj.updateMatrix();
  }
});

Don't set matrixWorldAutoUpdate = false unless you really know what you're doing — it cascades to children and you'll spend the rest of the day debugging why your nested groups aren't moving.

2. The shadow map is probably your bottleneck

Run the Chrome WebGL profiler. If your scene has shadows, there's a 60% chance the shadow map render pass is your most expensive draw.

Things that helped:

  • Smaller shadow maps. We were running 2048×2048 directional light shadows. Dropped to 1024×1024 — visible diff was minimal once we tuned bias, frame time dropped 3-4ms.
  • shadow.autoUpdate = false for the static parts of the scene. We render the shadow map once, freeze it, and only re-render when the lighting genuinely changes (which is rarely).
  • Cull aggressively. directionalLight.shadow.camera has a frustum. By default it's huge. Tighten it to just what your scene needs.

Combined: about 5ms saved on the shadow pass.

3. Texture memory is a perf metric, not a quality metric

We had source textures at 4096×4096 because "the artists made them that big". On screen, they were rendered at sizes where the user could see maybe 512 pixels of them at once.

Two things help here, both unsexy:

  • Generate mipmaps and let the GPU pick the right level. This is on by default in Three.js. The bug was we had texture.minFilter = THREE.LinearFilter set on a few textures, which disables mipmapping. Setting it back to LinearMipmapLinearFilter saved ~2ms by reducing memory bandwidth.
  • Compressed textures (BasisU / KTX2). Pipeline change, but worth it. We went from 380 MB texture memory to 92 MB. The GPU is happier, the CPU upload is faster, and the visual quality difference is invisible.

4. The post-processing pipeline lies about its cost

We had three passes: render scene → bloom → SMAA. Each pass renders to a full-screen quad at full resolution. Combined, this was ~4ms on M1. On lower-end hardware it was the entire frame budget.

What helped:

  • Half-resolution bloom. Bloom is naturally blurry. Render it at half-resolution, upscale on composite. Zero visual difference, ~60% reduction in bloom cost.
  • Don't run post-processing in offscreen browser tabs. Detect with document.visibilityState and requestAnimationFrame throttling. Saves laptop fans during the 80% of the time the user has another tab open.
  • Skip SMAA on retina/high-DPI displays. The pixel density does the antialiasing for free. We disable SMAA when devicePixelRatio >= 2.

What didn't work

For completeness, things I tried that didn't move the needle:

  • Frustum culling tweaks. Three.js does this already and does it well. My attempts to "improve" it were either bug-introducing or net-zero.
  • Manual draw call merging. I rewrote a chunk of the geometry pipeline to merge static meshes. Got a 0.5ms win, but it made the code so ugly that one of the 3D artists couldn't iterate on placement. Reverted.
  • InstancedMesh for the gallery items. This is the one every blog post recommends. It didn't help us because our items have different materials, and InstancedMesh requires a single material. We'd have had to bake material parameters into vertex attributes — complex, and the savings were marginal because we only had 80 instances, not 8000.

Tooling I keep open

  • Chrome WebGL Profiler — built into DevTools. Use it.
  • Spector.js — for capturing single-frame analysis when the live profiler isn't enough.
  • renderer.info — log it once per second during development. Watch for unexpected programs or geometries counts.
  • A perf budget logger — I open-sourced a small one called webgl-perf-budget. Logs to console when you go over your budget. Stops surprises in production.

The big-picture lesson

Three.js performance work isn't about exotic techniques. It's about measuring, then removing work. Most of what I described above is deletion: don't compute matrices, don't render at full res, don't keep huge textures. The fastest code is the code you didn't run.

Also: ship a budget. Not a target ("60 fps"), an active runtime check. Things regress. People add features. Without a budget, you'll be back at 24 fps in a year and you won't know which commit caused it.
