next-typed-routes

Type-safe routing for Next.js App Router. Compile-time-checked links, params, and route names — derived from your filesystem.

TypeScriptNext.jsCodegen
View on GitHub

The problem

The Next.js App Router is great. Its routing API isn't. <Link href="/posts/123" /> takes any string. Refactor a route from /posts/[id] to /articles/[slug], and your Links break silently at runtime.

Existing solutions either require you to write your routes twice (once in the filesystem, once in a config) or are tied to deprecated stacks. I wanted something that:

  • Reads my app/ directory as the source of truth
  • Generates types automatically
  • Catches missing/wrong route params at compile time, not runtime
  • Supports App Router patterns including catch-all and route groups

The approach

Two pieces:

1. The codegen

A small CLI that scans app/ for page.tsx files and emits a routes.gen.ts with a discriminated union of route patterns. Run it on dev startup, watch for changes, and let TypeScript do the rest.

routes.gen.ts (auto-generated)
// AUTO-GENERATED. Do not edit.
export type Routes =
  | '/'
  | '/about'
  | '/posts'
  | '/posts/[slug]'
  | '/posts/[slug]/comments'
  | '/(marketing)/pricing'  // route groups stripped at runtime
  | '/files/[...path]'      // catch-all
  ;

2. The route() helper

Where the magic happens. Uses TypeScript template literal types to extract param names from a route pattern and require them at the call site:

route.ts
type ExtractParams<S extends string> =
  S extends `${string}[${infer P}]${infer Rest}`
    ? P extends `...${infer R}`
      ? { [K in R]: string[] } & ExtractParams<Rest>
      : { [K in P]: string } & ExtractParams<Rest>
    : Record<never, never>;

export function route<S extends string>(
  pattern: S,
  params: ExtractParams<S>,
): string {
  let result: string = pattern;
  for (const [key, value] of Object.entries(params)) {
    if (Array.isArray(value)) {
      result = result.replace(`[...${key}]`, value.join('/'));
    } else {
      result = result.replace(`[${key}]`, String(value));
    }
  }
  return result;
}

The cool part: TypeScript infers the required params from the route string. So:

  • route('/posts/[slug]', { slug: 'hello' }) → ✅ OK
  • route('/posts/[slug]', {}) → ❌ Type error: missing 'slug'
  • route('/posts/[slug]', { slug: 'hello', extra: 'no' }) → ❌ Type error: 'extra' not allowed
  • route('/typo', {}) → ❌ Type error: route doesn't exist

Edge cases that mattered

Catch-all routes. /files/[...path]/page.tsx generates a route where path is string[], not string. Initial version got this wrong; #1 was a bug report from real usage.

Route groups. app/(marketing)/about/page.tsx serves at /about, not /(marketing)/about. The codegen strips parenthesized segments. Took a couple of iterations to get this right for nested groups.

Optional catch-all. [[...slug]] means the param is optional. The generated type is string[] | undefined.

I use this on three personal projects. Day-job stack at Shopify uses a different abstraction, but the core idea — derive types from the filesystem — has been my hill to die on for years.

Lessons

Codegen is unreasonably effective for type safety. Once you've crossed the build-step Rubicon, deriving types from filesystem layout opens a lot of doors. You can do this for routes, for translation keys, for design tokens, for env vars.

Template literal types are powerful enough to make codegen optional. If your pattern strings are literal in source code, you can skip the codegen entirely and let TypeScript infer everything. The codegen exists for the Routes union — listing all valid routes — which TypeScript can't derive from the filesystem.

What's next

I'd like to extend this to route metadata: layout-level config (auth requirements, prefetch behavior) attached to the type system so tooling can read it. But that's a bigger project and I haven't had a clear use case yet.
